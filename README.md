# 🏋️ Gym Management System

Полнофункциональная система управления спортивным залом. Предназначена для учета клиентов, управления абонементами, регистрации посещений и разграничения прав доступа персонала.

## 💻 Требования к системе

Для запуска проекта в режиме разработки необходимы следующие компоненты:

| Компонент | Рекомендуемая версия | Примечание |
| :--- | :--- | :--- |
| **.NET SDK** | 10.0.x | Для сборки и запуска Backend |
| **Node.js** | 20.x или 24.x (LTS) | Для сборки и запуска Frontend |
| **База данных** | PostgreSQL 15+ | **Рекомендуется:** через Docker Desktop. **Альтернатива:** локальная установка СУБД. |
| **Пакетный менеджер** | npm 10+ | Для установки зависимостей фронтенда |

## 🧠 Принципы бизнес-логики и архитектуры

1. **Разделение ответственности (SoC):** Контроллеры отвечают только за HTTP-маршрутизацию. Бизнес-логика инкапсулирована в `Services`. Валидация DTO вынесена в `FluentValidation`.
2. **Мягкое удаление (Soft Delete):** Сущности `Client`, `Employee`, `SystemUser` не удаляются физически. Используется флаг `is_active` / `is_deleted` для сохранения истории и целостности связанных записей (например, посещений).
3. **Гибкая модель пользователей:** Сущности `SystemUser` (учетная запись) и `Employee` (физическое лицо) разделены. Поле `employee_id` в `SystemUser` опционально, что позволяет создавать обезличенные учетные записи (например, общий логин для ресепшена).
4. **Жизненный цикл абонементов:** При создании нового абонемента система автоматически рассчитывает `end_date` (single: +30 дней, month: +30 дней, year: +365 дней). Предыдущий активный абонемент клиента автоматически переводится в статус `completed`.
5. **Целостность данных:** Уникальность телефонных номеров контролируется на уровне БД (UNIQUE constraint) и дублируется валидацией DTO.

## 🚀 Быстрый запуск (Рекомендуемый способ через Docker)

Этот способ автоматически создаст базу данных, таблицы и наполнит их демо-данными за одну команду.

### Шаг 1: Запуск базы данных
Убедитесь, что Docker Desktop запущен. В корне проекта выполните:
```bash
docker compose up -d
```
*Контейнер PostgreSQL автоматически выполнит скрипты из папки `docker-entrypoint-initdb.d`, создаст структуру и добавит тестовые данные.*

### Шаг 2: Учетные данные БД
Логин и пароль для подключения к СУБД находятся в файле:  
📄 `db_sql_scripts/gym_app_user.txt`

### Шаг 3: Запуск Backend
Перейдите в папку API и запустите проект (миграции выполнять не нужно, таблицы уже созданы скриптом):
```bash
cd GymApp.Api
dotnet run
```
*API будет доступен по адресу: `http://localhost:5144` (Swagger: `http://localhost:5144/swagger`)*

### Шаг 4: Запуск Frontend
Откройте новый терминал:
```bash
cd gym-app-frontend
npm install
npm run dev
```
*Интерфейс будет доступен по адресу: `http://localhost:5173`*

## 🔄 Альтернативный запуск (Без Docker)

Если Docker не установлен, выполните следующие шаги:
1. Установите PostgreSQL 15+ локально.
2. Создайте базу данных `gym_db` и пользователя `gym_app_user` (пароль из `gym_app_user.txt`).
3. Откройте любой SQL-клиент (DBeaver, pgAdmin, psql) и выполните скрипты **строго в этом порядке**:
   - Сначала: `db_sql_scripts/01_db_structure.sql` (создаст таблицы)
   - Затем: `db_sql_scripts/02_seed_data.sql` (добавит демо-данные)
4. Далее следуйте Шагам 3 и 4 из инструкции выше.

## 🧪 Тестирование

### Unit-тесты
Проект включает покрытие бизнес-правил валидации с помощью `xUnit` и `FluentValidation.TestHelper`. Тесты изолированы и не требуют подключения к БД.

**Запуск тестов:**
```bash
cd GymApp.Tests
dotnet test --verbosity normal
```

### Матрица тестирования (Use Cases)

| ID | Модуль | Сценарий (Use Case) | Ожидаемый результат |
| :--- | :--- | :--- | :--- |
| **UC-01** | Auth | Вход с валидными/невалидными данными | Возврат JWT-токена или HTTP 401 Unauthorized. |
| **UC-02** | Auth | Попытка доступа оператора к `/api/users` | Возврат HTTP 403 Forbidden (Policy-based authorization). |
| **UC-03** | Clients | Создание клиента с занятым телефоном | Возврат HTTP 400 с сообщением об ошибке валидации. |
| **UC-04** | Clients | Удаление клиента | Статус `is_deleted` меняется на `true`, запись исчезает из общих списков, но сохраняется в БД. |
| **UC-05** | Memberships | Покупка нового абонемента активным клиентом | Новый абонемент создан, предыдущий активный переведен в статус `completed`. |
| **UC-06** | Visits | Регистрация посещения по истекшему абонементу | Возврат HTTP 400. Посещение не регистрируется. |
| **UC-07** | Frontend | Адаптивность таблиц на мобильных устройствах | Таблицы имеют горизонтальный скролл, интерфейс не ломается. |

## 🗄️ Описание SQL-скриптов (`db_sql_scripts/`)

Скрипты пронумерованы для гарантированного выполнения в правильном порядке при инициализации Docker-контейнера.

| Файл | Назначение |
| :--- | :--- |
| `gym_app_user.txt` | Содержит логин и пароль пользователя СУБД для локальной разработки. |
| `01_db_structure.sql` | DDL-скрипт создания таблиц, индексов и ограничений (аналог миграций EF Core). |
| `02_seed_data.sql` | **Демо-данные.** Создает 4 сотрудников, 7 клиентов (разные статусы), 6 абонементов (active, completed, expired, cancelled) и 4 посещения. |


> ⚠️ **Примечание:** В проекте используются тестовые учетные данные для упрощения развертывания. 
> В production-среде необходимо заменить пароли и JWT-секрет на безопасные значения, 
> а файл `appsettings.json` добавить в `.gitignore`.
